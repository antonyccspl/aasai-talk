FRND-STYLE SOCIAL & REAL-TIME CALLING APP
FULL PRODUCT REQUIREMENTS & DEVELOPMENT PLAN
Technology: React Native + Supabase
Document Version: 1.0

============================================================
1. PROJECT OVERVIEW
============================================================

Build a mobile social communication platform where users can discover other users/hosts, see availability, chat in real time, and make direct one-to-one audio and video calls.

Core technology:
- React Native for Android/iOS mobile application
- Supabase Auth for authentication
- Supabase PostgreSQL for persistent data
- Supabase Realtime for presence, chat events, typing and realtime state
- Supabase Storage for media
- Supabase Edge Functions for secure backend logic
- Dedicated WebRTC/RTC provider for actual audio/video media
- FCM/APNs for push notifications
- Payment gateway for wallet recharge if calls are paid
- Separate web admin dashboard

IMPORTANT:
Supabase should NOT carry the actual audio/video media stream. Use a WebRTC/RTC service such as Agora, ZEGOCLOUD, Twilio, Stream, or a self-hosted WebRTC stack. For an MVP, a managed RTC provider is recommended.

8. AUDIO CALLING
============================================================

One-to-one audio calling.

Call flow:

1. Caller selects user
2. Backend checks receiver status
3. Backend creates/reserves call
4. Receiver is marked BUSY/reserved
5. Push notification is sent
6. Receiver sees incoming call
7. Receiver accepts/rejects
8. Backend generates RTC token
9. Both users join RTC channel
10. Call becomes CONNECTED
11. Call continues
12. One user ends call
13. Backend finalizes call
14. Duration is calculated
15. Billing is calculated server-side if paid
16. Call history is saved
17. Availability is restored

Audio controls:
- Mute/unmute
- Speaker
- End call
- Call timer
- Connection status

Call states:
- INITIATED
- RINGING
- ACCEPTED
- CONNECTING
- CONNECTED
- ENDED
- REJECTED
- MISSED
- CANCELLED
- FAILED
- BUSY

============================================================
11. CALL AVAILABILITY & RACE CONDITIONS
============================================================

Important requirement:

If two users try to call the same host at the same time, only one call should succeed.

Example:
User A calls Host X
User B calls Host X

Backend must atomically reserve Host X:
AVAILABLE -> RESERVED/BUSY

Do not implement this only in frontend code.

Possible backend approach:
- Transaction/locking
- Atomic database function
- Edge Function
- Call reservation record

 -> User receives notification

Payment should be confirmed through server-side verification/webhook.

============================================================
16. CALL BILLING
============================================================

Example pricing:
- Audio: Rs.5/minute
- Video: Rs.10/minute

Billing:
duration x rate = amount

Example:
7-minute audio call x Rs.5 = Rs.35

Requirements:
- Billing calculated on backend
- Use connected call duration
- Define minimum billing unit
- Define rounding rules
- Define grace period
- Define insufficient balance behavior
- Define refund rules
- Handle call failure
- Prevent duplicate billing
- Store billing reference

Do not trust client-side duration or price.

============================================================
17. PREPAID CALL LOGIC
============================================================

If the user pays before/during calls:

Required rules:
- Check minimum wallet balance before starting
- Reserve/authorize amount if business model requires it
- Deduct according to connected duration
- Stop or warn when balance is insufficient
- Finalize amount after call
- Refund unused reserved amount if applicable

Example:
Minimum required balance = Rs.20
Audio rate = Rs.5/min

If balance is Rs.10:
Do not allow the call if minimum balance is Rs.20.

Supabase Realtime handles realtime events/presence.

RTC provider handles actual audio/video.

Edge Functions handle sensitive business logic.

RULE 6:
Payment gateway handles payment collection.

Webhooks confirm payments.

Wallet changes happen server-side.

RULE 9:
Call billing happens server-side.

RTC tokens are generated server-side.

RULE 11:
RLS protects user data.

RULE 12:
